# ADR-0009: 10万枚の写真一覧を順序付き索引＋仮想ウィンドウで表示する

- Status: Accepted
- Date: 2026-10-23
- Supersedes: [ADR-0007](0007-photo-load-cap.md)

> 番号について: 計画時は ADR-0008 を予定していたが、ADR-0008 は既にプライバシーADR（[0008-privacy-parsed-events-only.md](0008-privacy-parsed-events-only.md)）で使用済みのため、次の空き番号 0009 を使用する。

## Context

ADR-0007 では、MVPの一覧・検索を `list_photos(300)` / `search_photos_text(300)` で最大300枚に制限した。目標は10万枚のライブラリだが、300枚を超える写真には検索条件を絞る以外に到達できず、初回表示では300枚分のサムネイルを同期的にデコードしていた。

100k対応では、次のUXを同時に満たす必要があった。

- 一覧・検索の全件に連続スクロールで到達できる。
- 右端の年レールが全件に対する現在位置を示し、年ラベルへのクリックとドラッグで任意の年へジャンプできる。
- 現在表示中の月をレール上に表示する。
- スクロール中にSQLiteクエリや画像デコードをUIスレッドで実行しない。
- メモリ使用量に上限を設ける。

issue #8 の当初案はキーセットページングだったが、キーセットは追記型フィード向きであり、任意位置へ飛べるレールのランダムアクセスUXとは相性が悪い。

## Decision

### 1. 順序付き索引スナップショット

一覧・検索のたびに、一致する写真の軽量な索引を1回だけ読み込む。

```rust
pub struct PhotoIndexEntry {
    pub id: i64,
    pub captured_at_utc: i64,
    /// ローカル撮影月を YYYYMM で表す（例: 202504）。
    pub captured_month: i32,
}
```

- `Db::photo_index(sort)` は `status = 'present'` の全件を、一覧と同じ順序で返す。
- `Db::photo_index_text(filter)` は検索条件に一致する全件を `captured_at_utc DESC, id DESC` で返す。検索条件の組み立ては既存の検索と共通化する。
- 索引は `Arc<PhotoIndex>` としてUIが保持する。100k件でも1件24バイト、約2.4 MBの想定。
- `captured_month` は `captured_at_local` から計算し、壊れたローカル時刻はUTCへフォールバックする。年レールは撮影者のローカル暦に従う。
- 行数・年バケット・レール位置は索引から正確に決まる。`uniform_list` の行数は最初のフレームから全件分ある。

### 2. 256枚ページキャッシュ

表示に必要な写真本体だけを主キーで取得する。

- 1ページ256枚、最大24ページ（6,144枚）。
- 表示範囲のページがキャッシュにない場合、描画中は `pending` に記録するだけにし、遅延コールバックで `Db::photos_by_ids` を実行する。
- 1回の遅延コールバックで最大2ページ。速いスクロールでも1フレームあたりのDB作業を数msに抑える。
- キャッシュはアクセス順LRU。`get_page` で参照したページを最近使用側へ移動し、`insert_page` で上限を超えた分を古い側から追い出す。これにより、下へスクロールした後に戻ったページが、後から到着した先読みページに押し出されない。
- 索引を差し替えた世代（`generation`）が古いページ到着は破棄する。

### 3. 非同期サムネイル

- 表示中のカードのサムネイルだけを要求する。キャッシュ済み・保留中・失敗済みのIDはスキップし、同時デコードは最大4件に制限する。
- デコードはバックグラウンドエグゼキュータで行い、`RenderImage` の生成だけをUIスレッドで行う。
- 192件のアクセス順LRU。選択中の写真はピン留めし、カードが画面外へスクロールしてもインスペクタ背景用のサムネイルを保持する。
- 失敗したIDは再試行しない。

### 4. 年レール

- 一覧と検索で同じ `YearRail` を使う。
- 年のラベル位置は「その年より新しい写真の累計枚数」に比例させる。写真が多い年ほど縦方向の領域が広くなる。
- 月はUTC順の索引ではなくローカル月でバケット化し、年をまたぐタイムゾーン境界で同じ年が分断されないよう、非連続のランを1バケットへ統合する。
- ラベルのクリックでその年の先頭写真へ、レール上のドラッグで任意の写真位置へジャンプする。
- 現在の先頭行の月を `YYYY年M月` のピルで表示する。ピルはスクロールに追従する。
- レールの描画は索引とスクロールハンドルのオフセットだけを読み、DBアクセスも画像デコードもしない。ラベルのテキストシェイピングは索引世代ごとに1回だけ行う。
- ジャンプ時のオフセットは GPUI の `ScrollHandle::max_offset()` が返す**非負のスクロール可能量**に合わせ、`-max_offset..0` にクランプする。`max_offset()` を負の値として扱わない。

### 5. 追加のみのマイグレーション

`SCHEMA_V3` で次の索引を追加する。テーブル定義の変更やデータ移行は行わない。

```sql
CREATE INDEX IF NOT EXISTS idx_photos_captured_id
    ON photos(captured_at_utc DESC, id DESC)
    WHERE status = 'present';
```

- 既存の `idx_photos_captured` は残す。
- 新規DBでは `user_version = 3`、既存DBでは起動時にV3だけを適用する。
- 索引は新しい順・古い順の全件スキャンと `status = 'present'` の条件を支える。

## なぜキーセット追記を採用しなかったか

キーセットページングは、カーソル以降を200枚ずつ追加する方式で、メモリは一定に保てる。しかし今回のレールUXには次の問題がある。

- 全件数が最後まで確定しないため、レールの位置・年ラベルの比率・残り件数を正確に出せない。
- 任意の年へジャンプするとバッファを置き換える必要があり、ジャンプ先より上へ戻るには逆方向のprepend経路が別途必要になる。
- 検索と一覧でアンカー管理が別々になり、重複・欠落の境界条件が増える。
- レールは「追記型フィードの続きを読む」ではなく「全件に対するランダムアクセス」なので、全件の軽量索引を持つ方式の方が要件に合う。

ハイブリッド案（キーセット＋別の年索引）も検討したが、順序の真実が2箇所になり、ジャンプ後の双方向再アンカーが必要になるため採用しなかった。

## 測定結果（release、100k合成DB）

2026-10-23、開発機のreleaseビルドで測定した。数値は代表値であり、マシン負荷で変動する。

| 項目 | 結果 | 補足 |
|---|---|---|
| `photo_index` 100k | 61.6 ms | releaseベンチマーク。UIの再読込は51–55 ms |
| `photos_by_ids` 256 | 0.58 ms | UIのページ取得は0.41–0.57 ms |
| `photo_index_text` 100k | 60.9 ms | 529件の背景検索は0.78 ms |
| warm 初回フレーム | 229–243 ms | プロセス開始から最初のフレームまで |
| cold 初回フレーム | 1.4995 s | 1秒のスペック予算を超過 |
| 起動時のDB索引 | 約110–140 ms（warm 約108 ms / cold 約140 ms） | 起動時に同じ索引を二重に構築した合計 |
| 100k行のseed | 0.455 s | 単一トランザクション |

メモリは設計上の上限で、実測値ではない。

- 索引: 100k × 24バイト ≈ 2.4 MB。
- ページキャッシュ: 最大24 × 256 = 6,144枚。
- サムネイル: 192件（デコード済みRGBAで約50 MBの想定）。

**すべての予算を満たしたわけではない。** warmの初回フレームとDBクエリは予算内だが、coldの初回フレーム1.4995 sは1秒予算を超える。DB作業は約140 msに留まるため、超過分はウィンドウ生成・GPU初期化・シェーダ準備など起動側が支配的とみられる。ただし空DBでのcold baselineを取るまでは確定できない。起動経路のfollow-upとして、空DBと100k DBのcold比較、初期化処理の内訳測定を行う。

## 既知のフォローアップ

- **起動時の索引二重構築**: `App::new` と直後の `reload_all` が同じ `photo_index` を実行する。100kで約108 ms warm / 約140 ms coldの無駄がある。起動経路を統合する。
- **cold起動の1秒予算**: 上記のとおり未達。空DB baselineと起動処理の内訳測定が必要。
- **実ライブラリでのレール操作**: 100k合成DBで描画とプログラム的スクロールは確認したが、実ポインタでのドラッグ・年クリックは合成入力を受け付ける環境で再確認する。
- **コールドサムネイル**: 測定はキャッシュ済み256×144 WebPのデコード。フルサイズ画像からの初回 `ensure_thumbnail` は未測定。

## Consequences

- 一覧・検索の300枚上限を撤廃し、全件へ連続スクロールで到達できる。
- レールの位置・ジャンプ・現在月が全件に対して正確になる。
- 索引クエリは結果件数に比例する（100kで約62 ms）。写真の追加・削除時は索引の再構築が必要だが、インポートは2秒デバウンス＋アンカー保持、削除は該当エントリの除去で処理する。
- ページ取得は主キー検索なので、表示範囲外の写真行をメモリに持たない。
- UIスレッドからSQLiteクエリと画像デコードを排除した。
- 起動時に索引を二重に構築する既知の無駄と、cold起動の予算超過が残る。

## Alternatives

- **キーセット追記**: メモリ一定だが、全件数・レール位置・双方向ジャンプが不正確になる。却下。
- **キーセット＋別の年索引**: レールは作れるが、順序の真実が2箇所になり、ジャンプ後の再アンカーが複雑になる。却下。
- **全 `Photo` 行をメモリへ読み込む**: 実装は単純だが、パス・コンテキスト込みで数十MBになり、フィルタごとの再読込とサムネイルで重い。却下。
- **SQLite FTS5**: テキスト検索は速くなるが、一覧のページングとレールは別途必要。今回の範囲外。
