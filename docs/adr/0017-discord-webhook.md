# ADR-0017: Discord 連携は単一 Webhook と耐久 outbox で行う

- Status: Accepted
- Date: 2026-11-02
- Related: [#142](https://github.com/TommyZ-7/vrc-photon/issues/142), [#143](https://github.com/TommyZ-7/vrc-photon/issues/143), [#253](https://github.com/TommyZ-7/vrc-photon/issues/253)

## Context

VRChat の写真を Discord へ自動転送する要望（VRCNext 風）がある。一方、本アプリは
「写真・ログは外部送信しない」を設計方針としてきた（ADR-0008）。追加する場合も、
既定では何も送らず、ユーザーが明示的に有効化したときだけ送る必要がある。

方式の候補:

- ユーザーアカウントのトークンを使う self-bot: Discord の ToS 違反。
- Bot アカウント: 利用者ごとに Developer Portal での登録・招待が必要で、
  デスクトップアプリの初期設定としては重い。
- UI からの直接送信: UI を閉じると止まり、自動送信を継続できない。
- 圧縮ジョブに送信を相乗りさせる: 圧縮キューの完了待ちと outbox の相互待ちが
  発生し、削除時のドレイン条件も複雑になる。

さらに、送信は取り込み・圧縮をブロックせず、デーモン再起動や削除要求と
整合する必要がある。Discord には冪等キーがないため、再起動時に送信中だった
メッセージを自動再送すると二重投稿になり得る。

## Decision

- 単一の Discord Webhook を使う。連携はオプトインで、既定は無効。
  機能が無効、URL が未設定、または URL が不正な間はネットワーク送信を
  1 件もしない。
- Webhook URL は認証情報として `app_settings.discord_webhook_url` の独立キーに
  保存する。`AppSettings` の JSON には入れない。受け付けるのは HTTPS の
  Discord ホスト（`discord.com` / `discordapp.com` / `ptb.discord.com` /
  `canary.discord.com`）の `/api/webhooks/<id>/<token>` だけで、リダイレクトは
  追わない。UI では ID までと `••••` のマスク表示にし、ログ・outbox・IPC
  イベント・エラートーストに出さない。OS の資格情報ストア保存は将来の課題とする。
- 送信は SQLite の `send_outbox` に耐久化し、デーモンの単一ワーカー
  （`discord-send`）が実行する。UI は設定の保存と enqueue、IPC は起床通知
  だけを担う。
- 送信元は原画を優先する。上限は 20 MiB（`20 * 1024 * 1024` バイト）。
  超える場合や原画がない場合は、選択した連携プロファイルの既存 derivative、
  なければメモリ上エンコードへフォールバックする。圧縮ジョブは積まない。
- embed にはワールド名、撮影日時、任意でプレイヤー名（既定オフ）を入れる。
  送信先名はローカルのラベルで、Discord へは送らない。
- 自動送信はオフ／即時／待機の 3 択。初回に同意ダイアログを出し、
  `discord_auto_since` 以降に撮影された写真だけを対象にする。機能または
  Webhook の再開時は cutoff を now に更新し、無効期間の写真を
  バックログとして投稿しない。
- 削除要求は対象写真の `waiting` / `pending` / `failed` の送信をキャンセルし、
  `processing` は完了まで残す。アクティブな送信がある間は削除を開始しない。
  `failed` は削除をブロックしない。
- 429 は `retry_after`（1〜900 秒）に従い、attempts を増やさずワーカー全体を
  停止する。5xx／ネットワークは 2, 4, 8, … 秒（最大 300 秒）の指数バックオフ、
  429 を除く 4xx は terminal。再起動時に `processing` が残っていた場合は、
  二重投稿を避けるため `failed(interrupted)` にして自動再送しない。

## Consequences

- Webhook URL はローカル DB に残るため、DB バックアップを共有すると
  投稿先を操作できるトークンも渡ることになる。UI のマスクとログのサニタイズは
  できるが、バックアップの管理は利用者の責任になる。
- Webhook は 1 つだけ。写真ごとの振り分けや複数サーバーへの同時投稿はしない。
- 非公開インスタンスの写真を自動除外するルールはない。カードに注意書きを出す。
- 送信に失敗した行は自動では消えない。履歴から再送・取消でき、ワーカーが
  `sent` / `failed` にしたとき terminal 行を最新 500 件に切り詰める。
- 送信中は DB ロックを持たないため、大きな画像のアップロード中も取り込み・
  圧縮・UI は進む。
- デーモン再起動で送信中だった写真は「結果不明」として失敗になり、ユーザーが
  再送を判断する。二重投稿の可能性はゼロではない。

## Alternatives

- **self-bot**: ユーザーアカウントのトークンで投稿する。Discord の ToS 違反で、
  アカウント停止のリスクを利用者に負わせるため不採用。
- **Bot アカウント**: OAuth や Bot 招待の設定が必要になり、写真管理アプリの
  初期設定としては重い。Webhook ならサーバー管理者が URL を1つ発行するだけで済む。
- **UI プロセスから直接送信**: UI を閉じると送信が止まり、自動送信の
  「デーモンだけが動いている間も継続する」を満たせない。不採用。
- **圧縮ジョブの完了後に送信**: 既存パイプラインを再利用できるが、送信のたびに
  derivative が残り、圧縮キューと outbox の相互待ちが発生する。不採用。
- **複数 Webhook の登録**: 写真ごとの振り分け UI と設定が必要になる。初期実装の
  範囲を超えるため不採用。単一 URL の差し替えで対応する。
- **Webhook URL を `AppSettings` のフィールドに保存**: 実装は単純だが、
  `Debug` 出力や設定 JSON のエクスポートに URL が混ざる。独立キーに分離した。
