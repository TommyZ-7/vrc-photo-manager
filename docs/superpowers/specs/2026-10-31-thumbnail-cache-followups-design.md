# サムネイルキャッシュ追補 設計

- Issues: #187, #189, #190, #191
- 関連: #15 / PR #183
- 日付: 2026-10-31
- 状態: 未承認

## 目的

#15 / PR #183 で保留したサムネイル LRU の minor 4件をまとめて解消する。
LRU の近似方針（mtime）は維持しつつ、表示側の最近使用記録、削除タイミングと
走査コスト、失敗時テスト、想定内競合のログレベルを整える。

## ゴール

- メモリキャッシュから表示した場合も、1時間に1回までという既存の抑制を守って
  ディスク上の mtime を更新する。UI スレッドではファイル I/O をしない。
- デーモンの60秒ごとの定期全走査を廃止する。UI が直接生成したサムネイルは
  IPC でデーモンに通知し、上限超過時だけ全走査して削除する。
- 起動時の削除を初回スキャンより前に前倒しする。
- 削除失敗時に処理が継続し、次回パスで再試行されることをテストで担保する。
  Windows のファイルロック挙動もテストし、関連ファイル変更時のみ Windows CI で
  実行する。
- 削除競合から再生成で回復した場合は `debug`、回復できなかった場合のみ
  `warn` 以上で記録する。
- `thumbnail_cache_mb = 0`（無制限）では削除も全走査もしない。

## 非ゴール

- 厳密な LRU への変更（DB へアクセス日時を記録する方式）。
- サムネイルの形式・サイズ・生成アルゴリズムの変更。
- 設定画面での上限編集 UI の追加。
- DB スキーマ変更。
- デーモンと UI の同時起動を前提にしない外部ツールのキャッシュ書き込み対応。

## 現状

- `crates/core/src/thumbnail.rs` は mtime ベースの容量削除と
  `refresh_thumbnail_access` を提供する。削除失敗は debug ログで継続する。
- `crates/daemon/src/lib.rs` の `thumbnail_loop` は起動時に削除し、128件生成ごと、
  キューが500ms空になったとき、60秒ごとに全走査する。`run()` は初回スキャンの
  後にワーカーを起動するため、起動直後は上限超過が残る。
- `crates/ui/src/state/thumbnail.rs` はメモリ LRU（192件）を持ち、
  ディスクからデコードしたときだけ `refresh_thumbnail_access` を呼ぶ。
  メモリヒットでは mtime を更新しない。
- `crates/ui/src/app/photos.rs` はキャッシュミス時に自前で
  `ensure_thumbnail_in` を呼び、サムネイルを生成する。
- 削除直後のデコード失敗は1回だけ再生成して回復するが、最初の失敗で
  `warn` を出してしまう。
- 削除失敗のテストは「失敗しても継続する」経路が不足している。Windows の
  実行時テストは CI で動いていない。

## 検討した方式

### A. 増分管理 + 60秒の定期走査を維持

デーモンが生成バイト数を加算し、上限超過時だけバッチ削除する。UI 生成分は
60秒ごとの全走査で補正する。

- 利点: 変更がデーモン内で完結し、IPC を変えない。
- 欠点: 定期全走査が残る。実測では2万件で約25msだが、件数に比例する。

### B. 実測して現状維持を記録

コードを変えず、走査コストの計測結果と現状維持の妥当性だけを記録する。

- 利点: 最小コスト。
- 欠点: #187 / #190 / #191 は別途対応が必要。起動直後の上限超過も残る。

### C. UI → デーモン通知で定期走査を廃止（採用）

UI が生成したサムネイルのファイル数とバイト数を IPC でバッチ通知する。
デーモンは起動時の実測値を起点に、自身の生成分と通知分を加算し、削除後に
実測値へリセットする。定期全走査は行わず、上限超過時だけ全走査する。

- 利点: 通常時の全走査がゼロになる。UI 生成分も即座に上限管理へ入る。
- 欠点: IPC プロトコル変更（バージョン更新）が必要。通知漏れは起動時の
  全走査でしか補正できないため、上限は厳密ではなくソフト上限になる。

## 方式Cの詳細

### IPC (`crates/ipc`)

- `PROTOCOL_VERSION` を 2 に上げる。UI とデーモンは同時に更新する。
- `Request::ThumbnailsGenerated { files: u64, bytes: u64 }` を追加する。
  応答は `Response::Ok`。
- 既存の `Request` と同様に JSON の tagged enum で往復できることをテストする。
- 未知のリクエストは従来どおり接続終了となるため、バージョン不一致の
  メッセージで更新を促す既存経路に任せる。

### UI (`crates/ui`)

- core に `ensure_thumbnail_in_with_status` を追加し、実際にファイルを
  作成したか（`created`）と生成後のサイズを返す。既存の
  `ensure_thumbnail_in` はパスだけを返すラッパーとして残す。
  呼び出し前後の `is_file()` 判定では削除競合を正しく判定できないため、
  「生成した」という事実は core が返す。
- `decode_thumbnail` は `created == true` のときだけ生成後のファイルサイズを
  返す。メモリヒットやデモモードでは返さない。
- `App` は通知を `ThumbnailNoticeBatch` にまとめる。
  - 32ファイルまたは1 MiBに達したら即時送信する。
  - それ未満でも1秒後に送信する。
  - `ipc_connected == false` の間は保持し、再接続時（`Incoming::Connected`）に
    まとめて送る。デーモン未起動のまま終了した分は、次回起動時の全走査で補正する。
- 送信は既存の `wake_daemon` / `ipc_bridge::request` を使い、UI スレッドを
  ブロックしない。
- 重複通知（デーモンと UI が同じ ID を生成した場合など）は加算される。
  これは削除を早める方向にのみ作用し、削除後の実測リセットで解消する。

### デーモン (`crates/daemon`)

- `Daemon` に `thumbnail_external_bytes: Arc<AtomicU64>` を追加し、
  `IpcControl` と `thumbnail_loop` で共有する。
- IPC ハンドラは `bytes` を加算するだけ。ログは `debug`。
- `thumbnail_loop` は 500ms の待機ごとに外部通知分を `swap(0)` で取り込み、
  追跡バイト数へ加算する。
- 追跡状態は `limit_bytes` と `known_bytes: Option<u64>` で持つ。
  - 起動時・上限変更時・削除後の全走査では、走査前に外部通知分を取り込んで
    から `remaining_bytes` でリセットする。走査中に届いた通知は次ティックで
    加算される。走査に含まれたファイルを二重に数える可能性があるが、
    余分な全走査が1回増えるだけで、実測に基づく削除以上にはならない。
  - `limit_bytes == 0` は `None`（追跡しない）。無制限中の通知は破棄する。
  - 自身の生成時は生成後のサイズを加算する。
  - 削除後は `remaining_bytes` にリセットする。
- 削除トリガーは次の3つに整理する。
  - 128件生成したとき（`known_bytes` が上限を超えている場合のみ）
  - キューが500ms空になったとき（未処理の生成または外部通知があり、
    上限を超えている場合のみ）
  - 上限設定が変わったとき（即時）
- `THUMBNAIL_PRUNE_INTERVAL` と `periodic_due` を削除する。
- `run()` の先頭（`start_ipc()` より前）で起動時の削除を実行し、上限超過を
  初回スキャン中に残さない。キュー済みの import スキャンにも先行する。
  `thumbnail_loop` の起動時削除はテストと直接起動のために残す。
  `--once`（`run_once`）は従来どおり処理後の削除とし、常駐起動の前倒し対象外。
- 追跡値が実際より大きい場合は早めに削除されるだけで安全。実際より小さい場合は
  次回デーモン起動時の全走査で補正する。

### UI の最近使用記録 (#187)

- `thumbnail::ACCESS_REFRESH_AFTER` を公開する。
- `ThumbnailCache` に `last_disk_refresh: HashMap<i64, Instant>` と
  保留 ID の集合を追加する。
  - `insert` 時に現在時刻を記録する。
  - `get` のメモリヒット時、1時間以上経過していれば ID を保留集合へ入れ、
    その時点で記録時刻を現在時刻へ更新する（毎フレーム再予約しない）。
    ファイル I/O はしない。
  - 退避時に両方から削除する。
- ギャラリーは描画後に保留 ID を取り出し、`App` のメソッド経由で
  バックグラウンド実行にまとめて `refresh_thumbnail_access` を呼ぶ。
  デモモードでは何もしない。
- 実際の mtime 更新は `refresh_thumbnail_access` 側の1時間抑制にも従う。

### ログレベル (#191)

- キャッシュファイルが `ensure` 後に消えていて再生成に成功した場合:
  `debug`（想定内の削除競合）。
- 再生成で `Ok(None)`（元写真が存在しない・デコード不能）: `debug`。
  これは削除競合ではなく、既存の「元写真なし」経路と同じ扱い。
- 再生成で `Err`（I/O 失敗など）: `warn`。
- ファイルが存在するのにデコードできない場合: `warn`（破損など想定外）。
- 再生成後のデコードにも失敗した場合: `warn`。
- ログ出力を `decode_thumbnail_file` から呼び出し側へ移し、経路ごとに
  レベルを決める。

### 削除失敗テストと Windows (#190)

- `prune_thumbnails_in` の内部に削除関数を注入できる
  `prune_thumbnails_with` を設ける。公開 API と挙動は変えない。
- 追加テスト:
  - 1件の削除が失敗しても他の削除を継続し、報告値が実態と一致する。
  - 失敗したファイルが次回パスで再試行され、成功後に削除される。
  - Unix: 読み取り専用ディレクトリで削除に失敗しても継続する
    （root 実行など削除できた場合はスキップ）。
  - Windows: `share_mode(0)` で開いたファイルの削除が失敗し、ハンドルを
    閉じた次回パスで削除される。
- CI:
  - `changes` ジョブに `thumbnails` 出力を追加し、サムネイル関連ファイル
    （`crates/core/src/thumbnail.rs`、`crates/ui/src/state/thumbnail.rs`、
    `crates/daemon/src/lib.rs`、`crates/ipc/src/protocol.rs`、
    `.github/workflows/ci.yml`）が変わった PR で true にする。
  - 既存の `ipc-windows` ジョブに、`thumbnails == 'true'` のときだけ
    `cargo test -p vrc-photo-core thumbnail::tests` を実行するステップを足す。
    新しい必須チェックは増やさない。

## テスト

- core:
  - 削除失敗の継続・再試行（注入）。
  - Unix の権限エラー、Windows のロック（各プラットフォームで実行時のみ）。
  - mtime 更新の既存テストが引き続き通る。
- IPC:
  - `ThumbnailsGenerated` の JSON 往復。
  - ハンドラが外部バイト数を加算する。
- daemon:
  - 外部通知で上限を超えたときに削除が走る。
  - 上限以下の外部通知では削除しない（追跡値の単体テスト）。
  - バッチ・アイドル・設定変更の各トリガー。
  - 定期実行トリガーが存在しないこと。
- UI:
  - 通知バッチの閾値と取り出し。
  - 生成時だけサイズを返し、キャッシュヒットでは返さない。
  - メモリヒットの1時間抑制と保留 ID の重複排除。
  - 描画後の保留 ID 回収。
  - 削除競合で再生成する既存テストと、破損ファイルでは再生成しないテスト。
- 全体:
  - `cargo fmt --all -- --check`
  - `cargo clippy --workspace --all-targets -- -D warnings`
  - `cargo test --workspace`
  - 関連ファイル変更時の Windows CI。

## リスク

- **プロトコル不一致**: UI とデーモンを同時更新する。既存のバージョン不一致
  メッセージで旧デーモン利用者に更新を促す。
- **通知漏れ**: 上限をわずかに超えた状態が次回起動まで残り得る。UI が接続中に
  終了して1秒バッチが未送信の場合も最大31ファイル/<1 MiB の未計上を許容する。
  起動時の全走査で必ず補正する。ソフト上限として受け入れる。
- **重複加算**: 早めの削除が起きるだけで、削除後の実測リセットで収束する。
- **メモリヒットの mtime 更新**: 1時間に1回・ID 単位に抑え、UI スレッドでは
  I/O しない。保留集合はメモリ LRU の件数（192）を超えない。
